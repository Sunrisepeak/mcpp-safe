## 设计核心（沿用原方案，不变）

完全替换 Clang，改变的是"由谁来实现"，不改变"MC++ 是什么"。原方案的设计核心仍然是本路线的设计核心，每个里程碑、每个工作项都要服从它。来源：[可行性调研](2026-09-28-mcpp-safe-feasibility.md)（mcpp-safe 的出发点）、[架构方案](2026-09-28-mcxx-architecture-plan.md)（目标、原则 P1–P13、组件、扩展点）、[自研前端讨论](2026-09-28-own-cpp-frontend-discussion.md)（§6 技术选型、§8–§9 的决定）。

| 核心 | 原方案出处 | 在本路线里的要求 |
|---|---|---|
| C1 **安全**：在编译期强制禁止特性、类型和库，做生命周期检查（mcpp-safe 的出发点） | 可行性调研 §0、§3.3；架构方案 §2 目标 3、P4；讨论 §8.3 | 自研前端在解析和语义阶段**原生**执行门禁，不是事后再遍历一遍 AST；每个里程碑的第一个验收对象都是 `safe` profile；Safe 的扩展能力在阶段 Ⅰ 先在 Clang 内核上做完（生命周期 v0、v1、借用检查，MF.4），阶段 Ⅱ 改为跑在 MCIR 上（K3） |
| C2 **插件系统**：编译器本身就是插件系统；内置功能也是 provider；插件可以控制、扩展、覆盖 | 架构方案 §2 目标 5、P5、P8、P11、§9.4 | 新能力先考虑能不能做成插件（P8），核心里不写特判：<br>- C++26/29 每一代是一个插件包；<br>- 分析 pass 和后端都是扩展点（阶段 Ⅰ 在 Clang 的 CFG 和 LLVM IR 上，阶段 Ⅱ 在 MCIR 上，接口相同）；<br>- GPU 是区域插件 |

| C5 **模块优先**：只接受模块；import 走模块图和 IFC；模块是方言的基本单位 | 架构方案 §2 目标 1；MC2 | M6 支持 classic 代码，是为了编译 `std`、C 库和平台头文件，不改变"MC++ 方言就是模块"的定位；IFC 带方言信息（K1、K7） |

| C7 **规范和可追溯**：跨边界的数据都有规范（MC1–MC6）；要求带 id；有一致性测试 | P3；`specs/` | 新规范：<br>- MC7 MCIR（M4）；<br>- MC4 的语言扩展点（M3.0）；<br>- MC2 增加模板和内联函数体（M5）。<br>每个验收项都引用要求 id |

### 实现标准：全部用 C++ Modules

- **只写模块**：本项目自己的代码只写模块。每个组件是 `export module mcxx.<组件>;` 加分区（`:lex`、`:syntax` 等），实现单元都是模块实现单元；标准库用 `import std;`，不 `#include`。
- **头文件只在包装模块里**：头文件只能出现在包装第三方 C/C++ 库的那个模块的全局模块片段里。
  - Clang 和 LLVM：只在 `mcxx.backend.clang`，以及将来的 `mcxx.codegen.llvm`。
  - IFC SDK：只在 `mcxx.ifc`。
  - 系统调用：只在平台层。
  - 现在 `modules/diagnostics/src/view.cpp` 直接包含了 `<unistd.h>`，按 P9 移到平台层，在 M3 期间清理。
- **核心部分零头文件**：自研前端（`mcxx.frontend` 及其各层）、MCIR（`mcxx.ir`）、插件 SDK、语言插件（`plugins/lang/*`）都不包含任何头文件。
- **按关注点拆分区**：每个文件不超过约 2000 行。
- **由 lint 强制**：`lint.py` 加一条 `modules-only` 规则检查以上各点（M3.0 期间加）。
- **最终检验**：自举（MR.2）就是 MC++ 用自己的前端编译自己的模块代码，这也是"全部用模块实现"的最终检验。

## 0. 终点（完成的定义）

| # | 终点 | 怎么判定 |
|---|---|---|
| T1 | 自研前端编译全部 C++：C++23，加上 C++26、C++29 已确定的核心语言特性；模块代码和 classic 代码（全局模块片段、头文件、libc++ 的 `std` 模块、各平台 C 库和 SDK 头文件用到的 GNU/Clang 扩展子集）；以及 C 模式（openkal-musl、LLVM 里的 C 源码） | MR 的验收项 |
| T2 | `mcxx` 不再链接 Clang 的前端库（clangLex、Parse、Sema、AST、Serialization、CodeGen、Frontend、Driver 等）。LLVM 的优化器、后端和目标文件写出保留（和 rustc、Zig 一样） | 链接图和 `nm` 检查 |
| T3 | 自举：Clang 版 mcxx 构建出 stage1，stage1 构建 stage2，stage2 构建 stage3，stage2 和 stage3 的目标文件逐字节相同；三个平台 | CI |
| T4 | MC++ 的核心能力（§6）全部运行在自研前端上 | 各项的验收 |

**仍不做**：ObjC/ObjC++、OpenMP、CUDA/HIP/OpenCL/HLSL 的语言模式（GPU 走区域插件，§6 K6）。**待决**：MSVC ABI（§8 第 1 条）。

## 1. 规模（实测和估计）

| 对象 | 行数 | 说明 |
|---|---|---|
| mcpp | 约 12.2 万 | 难度的标尺 |
| Clang 23.1 `lib/`：Sema / AST / CodeGen / Driver / Parse / Serialization / Frontend / Basic / Lex | 33.2 万 / 19.6 万 / 21.2 万 / 7.0 万 / 5.0 万 / 4.3 万 / 4.1 万 / 3.5 万 / 3.2 万 | 本机统计（`forks/llvm-clang-dev/llvm/clang/lib`），不含头文件（`include/clang` 另有约 28.6 万） |
| GCC 16 的 C++ 前端 | 约 40.7 万 | 不含代码生成 |
| 自研前端现在 | 约 1.0 万（`modules/frontend/src`） | 词法、预处理（模块代码用到的部分）、声明级解析、名字查找、部分表达式类型 |

Clang 的大部分体量花在本路线不做的东西上（ObjC、OpenMP、CUDA、OpenCL、HLSL、MSVC ABI、C 的旧模式）。只做 C++ 加 C、Itanium ABI、三个平台，估计如下：

| 里程碑 | 新增（估计） | 约合 mcpp |
|---|---|---|
| M3 语义核心 | 8 万–12 万 | 0.7–1.0 |
| M4 代码生成 | 6 万–10 万 | 0.5–0.8 |
| M5 模板和常量求值完整，能编译 `std` | 10 万–15 万 | 0.8–1.2 |
| M6 classic C++、扩展和 C | 6 万–10 万 | 0.5–0.8 |
| ML-F（C++26/29 在自研前端上） | 3 万–6 万 | 0.25–0.5 |
| MR 收尾 | 1 万–2 万 | 0.1–0.2 |
| **合计** | **34 万–55 万** | **2.8–4.5** |

合计和 GCC 的 C++ 前端同一量级。按"只要比 mcpp 复杂度低就不算难"的标尺：没有一个里程碑超过 1.2 个 mcpp，而且每个里程碑结束时都有能单独交付的东西。阶段 Ⅰ（§3）不在这张表里：它主要是 MSA 之上的功能代码，替换时保留。

## 2. 路线选择

### 2.1 先把功能全部做出来再逐步替换 Clang，还是先重写前端再做功能

| 路线 | 做法 | 功能什么时候能用 | 会扔掉的工作 | 风险 |
|---|---|---|---|---|
| **甲. 功能先行、逐层替换（采用）** | 阶段 Ⅰ 在 Clang 内核上把 MC++ 的全部功能做完，每项功能只通过 MSA 和规范（MC1–MC7）定义接口，并配上一致性测试集。阶段 Ⅱ 由自研前端一层一层接管同一批接口（从实现上逐步替换），每接管一层都要用这些测试集加上和 Clang 的差分来验收 | 从现在起陆续可用 | 只有 Clang 专用的部分会被扔掉：<br>- 适配层：现在约 5,000 行（`modules/backend/clang*`），阶段 Ⅰ 结束时估计 1.5 万–2.5 万；<br>- Clang fork 里自己写的语言特性：1.5 万–2.5 万。<br>合计不超过约 5 万行，约 0.4 个 mcpp | Clang 的东西渗进上层：靠 P1 和分层检查挡住（只有 `backend.clang` 能看到 Clang） |
| 乙. 先重写前端，再做功能 | 先把 34 万–55 万行的前端写完（§1），再在它上面做功能 | 2.8–4.5 个 mcpp 的工作量之后 | 不扔 | 这段时间里 MC++ 只是"Clang 加门禁"。前端是在不知道功能需要什么接口的情况下设计的，功能做起来以后再返工；C++ 一致性的参照（Clang）照样要用，而 MC++ 功能本身没有参照 |

**选甲，理由有四：**

1. **原架构就是按甲设计的**：MSA 是稳定层，规则、分析、插件、mcppls 只依赖 MSA（架构方案 §9.2：写在 MSA 之上的东西，切换时不用改）。
   - 现在 3 万行自己的代码里，只有约 5,000 行碰 Clang，其余约 2.5 万行替换时原样保留。
   - 阶段 Ⅰ 新写的功能也一样：功能逻辑留下，换掉的只是下面实现 MSA 的那一层。
2. **代价不对称**：甲多花约 0.4 个 mcpp，用来写 Clang 专用的部分；乙让全部功能晚 2.8–4.5 个 mcpp 才能用。
3. **功能先定型，前端设计才有依据**：阶段 Ⅰ 做出来的接口和测试集，就是自研前端的需求和验收标准。
   - 前端不需要猜要支持什么（门禁要在哪一层报、分析要什么样的 CFG、插件要哪些扩展点）。
   - 这正好避免了乙的返工风险。
4. **每一步都能度量**：每接管一层，都用同一份测试集、和同一个 Clang 做差分，一致率是客观的（P6）。乙要到最后才有整体可测的东西。

**甲不是"阶段 Ⅰ 做完才开始替换"**：阶段 Ⅱ 从现在起就并行推进（M3.0 已开始）。资源冲突时阶段 Ⅰ 优先，但阶段 Ⅱ 始终至少有 1 条工作线在做，因为它在通往终点的关键路径上（§6）。

### 2.2 C++26/29：两个前端都做，各自在合适的时机

这是 2.1 落到语言标准上的结果：
- **阶段 Ⅰ**：在 Clang fork 里做，即 ML-A。挑最省的来源：从 LLVM main 回移 4 篇；反射一族和展开语句从 clang-p2996 移植；`#embed` 和错误行为用 Clang 已有的机制；其余自己写，估计 1.5 万–2.5 万行，其中契约最大。
  - 这样做之后，使用者马上能用。
  - Clang fork 同时是自研前端实现同一篇论文时的参照答案（P6），在阶段 Ⅱ 一直被用到，到 MR 才退役。
- **阶段 Ⅱ**：自研前端在每篇论文所依赖的那一层建成时实现它，即 ML-F（§4）。
  - 反射、契约、常量求值中的异常会影响 AST 和常量求值器的结构，所以 M3.0、M3.6 的设计要给它们留好位置。

## 4. 节点：阶段 Ⅱ 逐层替换（从现在起并行）

自研前端一层一层接管 MSA 的查询，以及编译管线的各个阶段。每个节点的验收都由三部分组成：
- 阶段 Ⅰ 的测试集在"这一层不再使用 Clang"时仍然通过；
- 和 Clang 的差分一致率达到门槛；
- 语料上的结果。

已经接管的有：语法和大纲（M1.7、M1.8），声明和查找（M2，供服务端使用）。

| 节点 | 接管什么 | 接管之后 |
|---|---|---|
| M3 | 表达式和类型的事实（MSA 的表达式查询） | 门禁和规则先用前端的事实，前端说不确定的才交给 Clang（A3.1、A3.2） |
| M4 | CFG（MCIR 实现 MF.3 的接口），以及 MC++ 方言模块的代码生成 | 分析 pass（生命周期、借用检查）不再需要 Clang；后端扩展点接收由 MCIR 降级出的 IR |
| M5 | 模板和常量求值全部，能编译 `std` | 实例化委托去掉 |

## 8. 风险和待决事项

1. **MSVC ABI**。Windows 上 mcxx 的默认目标是 MSVC 的（23.1.0.9 起），因为 mcpp 在 Windows 上用 MSVC 的 STL 构建 `std` 模块。替换后有两种做法：自研前端支持 MSVC ABI（布局、修饰、异常各一套，估计 4 万–6 万行，作为 MR 之后的可选节点）；或者 Windows 上改用 libc++ 加 windows-gnu 的 `std`。M5 之前定下来。
2. **C 模式的范围**。T1 包含 C，因为工具链自己的 C 库（openkal-musl）和 LLVM 里都有 C 源码。只做 C17 和 C23，不做 K&R 和更早的模式。
3. **上游进展**。Clang main 在这期间会实现其中一些论文，届时用回移替换我们在 Clang 侧自己写的实现（ML-A 的来源表每次同步时更新）。
4. **测试语料的许可**。Clang 的测试是 Apache-2.0 WITH LLVM-exception，按固定修订只读取用；GCC 的测试套件是 GPL，不拷进本仓库，最多作为外部语料运行。
5. **本机资源**。磁盘剩余约 21 GB，Clang 的完整构建只在 CI 上做；本机 agent 只编译改动的单个源文件（用 `compile_commands.json` 里的命令）。
6. **阶段 Ⅰ 拖长**。功能一项一项做下去，可能一直挤占阶段 Ⅱ 的名额。对策：阶段 Ⅱ 始终保留至少 1 条工作线；★ MC++ 1.0 的范围只包括原方案已列的功能（C1–C9 加 ML），新的想法排到 1.0 之后。

## 9. 并行开发的波次（§0.5）

- **分工**：每个 agent 负责一个工作项，改动的文件不和别的 agent 重叠；在自己的 worktree 或 fork 分支上开发，由协调者合并。
- **并发**：同时最多 3 个子 agent（会话的上限），本机重的任务合计 ≤ 4 个。
- **协调者不空等**：子 agent 没有回复时，协调者自己做不和它们重叠的工作项，主要是 MF.0 的收尾和台账、合并、CI 跟进，以及较小的 MF 项。
